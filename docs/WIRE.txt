# Wire.txt — R3 v4 Engineering Protocol
# Referenced in CLAUDE.md. Required for all engineering tasks.
# Version: 1.0 | Updated: 2026-04-09

---

## Protocol Format

Every engineering response must follow this structure:

```
FILES READ:
  - path/to/file.ts (lines read)
  - path/to/other.ts (lines read)

FINDINGS:
  - What the code actually does
  - Bugs or issues found
  - Constraints identified

CHANGES:
  - Exact changes made (file, line, before → after)
  - Root cause of each fix
  - Fix rationale
  - Affected surface
  - Regression check

REMAINING AMBIGUITIES:
  - What is still unclear
  - What needs verification
  - What was deferred and why
```

---

## Hard Rules

### Before Every Write
1. Read the file first — `cat -n` for line numbers
2. Confirm exact anchor text before any `sed` or Python replace
3. State the root cause before writing the fix
4. State the fix rationale
5. State the affected surface
6. Take a timestamped backup before destructive operations:
   ```bash
   cp file.ts file.ts.bak-$(date +%Y%m%d_%H%M%S)
   ```

### After Every Write
1. Run `pnpm tsc --noEmit` — must be zero errors
2. Verify the change landed: `grep -n "changed_text" file.ts`
3. If TSC fails — read the error, find root cause, fix before proceeding
4. Never leave a TSC error and move on

### Patch Discipline
- Dry-run first, apply second
- Python file writes over `sed` for multi-line replacements
- Use `assert` in Python scripts to catch missing anchors before writing
- Verify line count after Python writes — confirm no lines were dropped
- Never use `sed` on content that may appear more than once

### Backup Protocol
- Before any destructive operation: timestamped backup
- Backup naming: `filename.ext.bak-YYYYMMDD_HHMMSS`
- Backup dirs naming: `.r3-[operation]-backups-YYYYMMDD_HHMMSS`
- Clean up backups after confirming the fix is stable

---

## Triple-Check Procedure

Before writing any code fix, verify three times:

1. **Read** — Does the file contain exactly the text you expect to replace?
2. **Count** — How many times does the anchor text appear? (Must be exactly 1)
3. **Consequence** — What breaks if the replacement is wrong?

If any answer is uncertain — read more of the file before proceeding.

---

## Common Failure Modes (Learned)

| Failure | Root Cause | Prevention |
|---|---|---|
| `sed` duplicates content | Pattern matched twice | Use Python with `replace(old, new, 1)` and `assert` |
| Python slice drops closing braces | Off-by-one on line indices | Verify line count in output. Use `.rstrip()` + append |
| TSC errors after patch | Didn't run `pnpm tsc --noEmit` | Always run TSC before posting results |
| Anchor not found | File changed since last read | Re-read file immediately before each write |
| Import added but not wired | Two separate edits required | Always check both import AND usage site |
| Export added but not imported | Forgot the consuming file | Grep for all import sites before declaring done |

---

## Verification Checklist (Before Closing Any Task)

- [ ] `pnpm tsc --noEmit` → zero errors
- [ ] `grep -n "changed_text" file.ts` → change confirmed
- [ ] No unintended duplicate content
- [ ] No missing closing braces or type exports
- [ ] Backup cleaned up or noted for hygiene script
- [ ] `python3 r3_hygiene.py` run if structural changes made

```
FILES READ:
  server/procedures.ts (full file, 51 lines)
  server/routers/mixer.router.ts (head -5 for export name)

FINDINGS:
  - mixerRouter is exported as `export const mixerRouter`
  - procedures.ts imports from ./routers/aiMix.router
  - No duplicate keys in appRouter object

CHANGES:
  server/procedures.ts:
    + import { mixerRouter } from "./routers/mixer.router";
    Root cause: router defined but never wired
    Fix rationale: client tRPC calls to mixer.* were 404ing
    Affected surface: all mixer tRPC procedures
    Regression check: pnpm tsc --noEmit → 0 errors

REMAINING AMBIGUITIES:
  - djRouter and aiMixRouter also appear unwired — verify before closing
```
